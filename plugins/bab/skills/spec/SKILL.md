# bab spec

이슈는 스펙을 관리하는 투두입니다. 결정, 수정, 취소의 이력이 모두 이슈 타임라인에 남아야 합니다. 이슈의 라벨, 상태, 본문, 코멘트는 사람이 바꿔도 되고 에이전트가 바꿔도 됩니다. 누가 바꾸든 근거를 코멘트로 남깁니다.

## 스펙 필수 항목

| 항목 | 본문 제목 | 확인 방법 |
| --- | --- | --- |
| 왜 | `# 왜` | 본문에 섹션이 있고 비어 있지 않음 |
| 무엇을 | `# 무엇을` | 본문에 섹션이 있고 비어 있지 않음 |
| 어떻게 | `# 어떻게` | 체크리스트 항목이 1개 이상 |
| 관련 wiki | `# 관련 wiki` | `wiki/` 경로가 1개 이상 |
| 검증 기준 | `# 검증 기준` | 비어 있지 않음 |
| 중요도 | 라벨 `P0`~`P3` | 정확히 1개 |
| 상태 | 라벨 `status:*` 또는 Closed 사유 | 열린 이슈는 정확히 1개 |

## 상태 모델

| 상태 | GitHub 표현 | 누가 바꾸나 |
| --- | --- | --- |
| 등록 | Open + `status:proposed` | AI·사람 |
| 확정 | Open + `status:decided` | 사람 또는 에이전트 |
| 진행 | Open + `status:in-progress` | `/bab:sync` |
| 완료 | Closed as completed (PR의 `Closes #N`) | PR 머지 |
| 재오픈 | Reopen 후 다시 확정 | 사람 또는 에이전트 |
| 취소 | Closed as not planned | 사람 또는 에이전트 |

- 확정, 클로즈, 캔슬, 재오픈은 사람이 GitHub에서 직접 해도 되고 에이전트가 해도 됩니다. 에이전트는 사용자가 지시했을 때, 또는 근거가 갖춰졌다고 판단했을 때 합니다. 예를 들어 필수 항목이 모두 있고 관련 wiki가 완결성 검사를 통과한 이슈는 에이전트가 확정할 수 있습니다.
- 상태를 바꾼 쪽은 사유 코멘트에 행위자(사람 또는 에이전트)와 근거를 적습니다. 이슈 타임라인만 읽어도 누가 왜 바꿨는지 알 수 있어야 합니다.
- 본문 제목은 h1(`# 왜`)로 씁니다. 옛 형식인 h3(`### 왜`) 본문도 같은 섹션으로 읽습니다.
- 중요도 라벨은 CI(`bab` 워크플로)가 본문의 `# 중요도` 값으로 자동으로 맞춥니다. 이슈가 닫히면 CI가 `status:*` 라벨을 뗍니다.
- `no-spec` 라벨은 이슈 없이 하는 작은 수정(오타, 문서 정리)의 PR에만 붙입니다. 동작이 바뀌는 수정에는 붙이지 않습니다.
- `drift` 라벨 이슈는 CI의 드리프트 감시가 등록합니다. 본문의 "어떻게"에서 방향(코드를 wiki에 맞춤 / wiki를 바꿈)을 고르고 확정합니다. 고르는 쪽과 확정하는 쪽은 사람이어도 되고 에이전트여도 됩니다. wiki를 바꾸는 쪽이면 스펙 변경이므로 이유를 코멘트로 남깁니다. 확정 전에 드리프트가 해소되면 CI가 이슈를 닫습니다.
- `blocked` 라벨은 `/bab:sync`가 중단한 이슈에 붙습니다. 코멘트의 사유가 해결되면 사람이나 에이전트가 라벨을 떼고, 이슈는 스펙 큐(`/bab:sync next`)에 다시 들어갑니다.
- 상태를 바꿀 때는 항상 사유 코멘트를 먼저 남깁니다. 사유가 없으면 사용자에게 묻습니다.

## 작업 1. 스펙 등록

1. 대화로 필수 항목을 채웁니다. 빈 항목이 있으면 질문합니다. 추측해서 채우지 않습니다.
2. 관련 wiki 경로는 `wiki/index.md`를 읽고 기존 페이지에서 고릅니다. 새 페이지면 만들 경로를 적습니다.
3. 본문은 [`../wiki/references/writing-rules.md`](../wiki/references/writing-rules.md)의 한글 작성 규칙을 따릅니다.
4. 초안을 보여 주고 사용자의 확인을 받은 뒤 등록합니다.

```bash
gh issue create --title "[스펙]: <제목>" --body-file <초안 파일> --label status:proposed --label <P0~P3>
```

본문은 이슈 템플릿(`spec.md`)과 같은 h1 섹션을 씁니다. `# 종류`, `# 왜`, `# 무엇을`, `# 어떻게`, `# 중요도`, `# 관련 wiki`, `# 검증 기준`입니다.

## 작업 2. 이슈 확인

읽기 전용입니다.

- 단일 이슈: `gh issue view <N> --json number,title,body,labels,state,stateReason,comments`로 읽고 필수 항목 표를 기준으로 판정합니다.
- 현황: `gh issue list --state all --limit 100 --json number,title,labels,state,stateReason`으로 상태별 개수와 누락 항목이 있는 이슈를 정리합니다.

```text
## 스펙 현황

| 상태 | 개수 | 이슈 |
| --- | --- | --- |
| proposed | 2 | #12, #15 |
| decided | 1 | #9 |
| in-progress | 1 | #7 (PR #20) |

필수 항목 누락
| 이슈 | 누락 |
| --- | --- |
| #15 | 검증 기준, 중요도 라벨 |
```

## 작업 3. 상태 전이

에이전트가 상태를 바꿀 때 따르는 순서입니다. 사용자의 지시가 있거나, 아래 조건을 에이전트가 확인했을 때 수행합니다.

| 지시 | 순서 |
| --- | --- |
| 확정 | 필수 항목을 확인합니다. 빠진 항목이 있으면 확정하지 않고 무엇이 빠졌는지 코멘트로 남깁니다 → 확정 코멘트 → `gh issue edit <N> --remove-label status:proposed --add-label status:decided` |
| 취소 | 사유 코멘트 → `gh issue close <N> --reason "not planned"` → `status:*` 라벨 제거 |
| 재오픈 | 바뀐 스펙을 본문에 반영 → 사유 코멘트 → `gh issue reopen <N>` → 사용자가 다시 확정을 지시하면 위의 확정 순서를 따릅니다 |
| 수동 완료 | 사유 코멘트 → `gh issue close <N> --reason completed` |

사유 코멘트 형식은 다음과 같습니다.

```markdown
상태 변경: {이전} → {이후}

- 행위자: {사람 이름 또는 에이전트}
- 사유: {한 문장}
- 근거: {관련 코멘트·PR 링크}
```
