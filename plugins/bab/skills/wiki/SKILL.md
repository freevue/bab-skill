# bab wiki

wiki와 로컬 룰은 현재 개발 형상의 기준입니다. 과거 이슈나 기존 코드를 읽지 않아도 같은 이름, 계약, 동작과 유닛 관계를 재현할 수 있어야 합니다. wiki와 코드가 다르면 코드를 고칩니다.

## 구조

```plaintext
wiki/
├── index.md          # 전체 페이지 카탈로그 (분류별 표)
├── log.md            # 변경 기록 (append-only)
├── policy/{name}.md  # 정책: 규칙과 제약
├── feature/{name}.md # 기능: 유닛의 조합, 기능 TC
├── unit/{module}/{function}.md  # 유닛: 함수 하나, 유닛 TC
├── type/{module}/{Name}.md      # 타입: type · interface · enum 하나
└── reference/{name}.md          # 참고: 조사·정보와 출처
```

| 분류 | 담는 것 | TC | 템플릿 |
| --- | --- | --- | --- |
| 정책 | 제품과 시스템이 지켜야 할 규칙, 제약, 결정 | 없음. 규칙 ID를 기능 TC가 참조 | `templates/policy.md` |
| 기능 | 사용자가 쓰는 동작. 유닛을 조합해 만듦 | `FT-{이름}-NN` | `templates/feature.md` |
| 유닛 | 함수 하나. 이름, 매개변수, 타입, 설명, 내부 로직, 사용법, 사용처 | `UT-{함수}-NN` | `templates/unit.md` |
| 타입 | 데이터의 모양. 선언 전체, 필드별 의미, 사용처 | 없음 | `templates/type.md` |
| 참고 | 조사 결과와 배경 정보. 코드 형상의 기준이 되는 규칙은 담지 않음 | 없음 | `templates/reference.md` |

## 작성 규칙

- 템플릿의 섹션을 모두 채웁니다. 해당 없는 섹션은 지우지 말고 `해당 없음`과 이유를 적습니다.
- `reference`는 `wiki/reference/`에 두고 `index.md`의 `## 참고`에 한 번 연결합니다. `내용`과 `출처`를 적고 frontmatter에 `code`를 지정하지 않습니다. 계약이나 제품 규칙으로 확정한 내용은 정책·기능·유닛·타입 페이지에 옮기고 참고 문서에서 연결합니다.
- 유닛 페이지는 wiki와 로컬 룰만 보고 코드와 테스트를 쓸 수 있어야 합니다. 시그니처는 실제 TypeScript·JavaScript 선언으로 적습니다. 타입 표기가 없는 JavaScript는 타입 계약을 표에 적고, 선언과의 타입 비교는 미검증으로 남깁니다. 언어를 바꿔도 유지할 값의 제약, 기본값, 분기 순서, 경계와 실패 결과는 표·문장·TC로 명시합니다.
- 문서 완결성은 형상을 재현하는 기준입니다. `drift-check`는 아래 항목을 검사합니다. 동작의 의미와 필수 분기 순서는 에이전트가 별도로 확인합니다.
  - 유닛: 시그니처의 매개변수마다 `매개변수` 표에 같은 이름, 타입 계약, 비어 있지 않은 의미가 있습니다. 선언에 타입이 있으면 표와 일치해야 합니다. `반환` 표에는 `void`도 적습니다. `내부 로직` 번호 목록, `사용법` 코드 블록, `TC` 행이 있습니다.
  - 타입: `## 정의`의 필드나 enum 멤버마다 `필드` 표에 같은 이름, 같은 타입, 의미가 있습니다.
  - 기능은 `구성 유닛` 링크와 `TC` 행이 있고, 정책은 `규칙` 행이 있습니다.
  - 참고: `내용`과 `출처`가 비어 있지 않습니다. 코드 형상과 TC는 비교하지 않습니다.
  - 모든 분류 페이지: 템플릿 자리표시 `{...}`가 남아 있지 않습니다.
- 표의 매개변수 이름에는 `?`와 `...`을 붙이지 않아도 됩니다. 구조 분해 매개변수는 원문 그대로(`{ a, b }`) 적습니다.
- TC는 관찰 가능한 결과만 적습니다. 내부 구현을 확인하는 TC는 쓰지 않습니다.
- TC ID는 wiki 전체에서 유일합니다. 한 번 쓴 ID는 TC를 지워도 다시 쓰지 않습니다.
- 페이지끼리는 상대 경로 링크로 연결합니다. 기능 → 유닛, 기능 → 정책, 유닛 → 사용처 기능, 타입 → 사용처.
- 관계는 양쪽에 적습니다. 기능의 `## 구성 유닛`에 유닛을 넣으면, 그 유닛의 `## 사용처`에도 그 기능을 넣습니다. 한쪽에만 있으면 drift의 "사용처 불일치"가 됩니다.
- 기능 frontmatter의 `code`에는 그 기능을 실제로 구현한 파일을 적습니다. 구성 유닛은 그 파일들이 실제로 import하거나 호출하는 유닛과 같아야 합니다.
- 타입 페이지의 `## 정의`에는 선언 전체(필드 포함)를 실제 TypeScript 문법으로 적습니다. 필드를 바꾸는 것은 형상 변경이므로 wiki부터 고칩니다.
- 명세 frontmatter의 `issues`에 근거 이슈 번호를, `code`에 구현 파일 경로를 적습니다. 참고 문서는 `code`를 요구하지 않습니다. 구현에 필요한 정보는 해당 링크를 열지 않아도 명세와 로컬 룰에서 찾을 수 있어야 합니다.
- 외부 연결이 있으면 `issues`에는 내부 번호만 유지합니다. [연결 규약](../link/references/protocol.md)의 외부 연결 표에 상대 repo 이슈·관계·계약 위치·기준 커밋을 구분합니다. 필요한 계약은 지정한 외부 wiki 섹션을 작업 입력으로 읽습니다.
- 문장은 [`references/writing-rules.md`](references/writing-rules.md)의 한글 작성 규칙과 용어표를 따릅니다.
- UI 상태와 비동기 이벤트가 있으면 [`references/ui-async-pattern.md`](references/ui-async-pattern.md)의 표를 기능 흐름에 추가합니다. 각 이벤트의 함수 이름과 타입, 분기와 실패 결과는 유닛 페이지에 적습니다.
- 코드 JSDoc에는 한 줄 요약과 유닛 페이지 경로만 둡니다. 예: `/** 페이지 번호를 범위 안으로 맞춥니다. @see wiki/unit/page/clampPage.md */`

## spec 모드 (기본: 이슈 → wiki)

1. 이슈의 `Wiki` 경로가 대상 저장소의 `wiki/` 안에 있는지 확인합니다. 그 안의 페이지를 읽고, 없으면 템플릿으로 만듭니다.
2. 이슈에서 합의한 변경 의도를 현재 형상에 반영합니다. 정책과 기능부터 정하고, 유닛과 타입의 정확한 계약은 wiki에 적습니다.
3. 새 동작마다 TC를 추가하고, 바뀐 동작의 TC는 기대 결과를 고칩니다.
4. `index.md`의 정확한 분류에서 페이지를 찾고 관련 페이지를 읽습니다. 새 페이지와 링크를 실제 추가·변경·삭제에 맞춥니다. 중복 등록과 잘못된 분류를 없앱니다. 삭제한 페이지의 이전 경로는 이력으로 남깁니다.
5. `log.md` 끝에 `## [YYYY-MM-DD] spec | #N | 제목`과 바뀐 페이지 목록을 추가합니다. 삭제한 경로는 일반 텍스트나 이전 커밋 링크로 적습니다.
6. 이슈 범위 밖의 페이지는 고치지 않습니다. 필요해 보이면 보고만 합니다.

## ingest 모드 (예외: 기존 코드 → wiki)

bab을 처음 적용한 저장소에서 기존 코드를 문서화할 때 한 번만 씁니다. 사용자가 명시적으로 요청할 때만 실행합니다.

1. 사용자가 지정한 범위의 공개 함수를 찾습니다. ast-grep이 없으면 텍스트 검색 결과에서 실제 선언을 확인합니다.
2. 함수마다 유닛 페이지를 만듭니다. TC는 기존 테스트에서 옮기고, 테스트가 없으면 `TC 미정`으로 표시합니다.
3. 유닛을 묶어 기능 페이지를 만들고, 코드에서 드러난 규칙은 정책 후보로 표시만 합니다. 정책 확정은 사람이 합니다.
4. `log.md`에 `## [YYYY-MM-DD] ingest | - | 범위`를 남깁니다.
5. ingest가 끝난 범위부터는 spec 모드만 씁니다.

## lint

작성이 끝나면 이 스킬 폴더 기준 `../../ci/drift-check.mjs`로 wiki 구조와 형상을 검사합니다. 구현 전 명세에서 발견된 구현 누락은 별도로 기록합니다.

```bash
node <플러그인 루트>/ci/drift-check.mjs <저장소 루트>
```

구조만 볼 때는 `node <플러그인 루트>/skills/audit/scripts/wiki-check.mjs <저장소 루트>/wiki`를 씁니다.

결과는 [공통 브리핑 규칙](../setup/assets/claude-section.md#최종-브리핑)에 따라 전합니다. 바뀐 명세와 검사 결과를 설명합니다. 코드와 대조하지 못한 항목은 미검증으로 남깁니다.
