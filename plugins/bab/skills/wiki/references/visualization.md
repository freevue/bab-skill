# 시각화 기준

사용자가 시각화를 요청하거나 관계·분기를 그림으로 확인해야 할 때 읽습니다. 질문에 필요한 관점만 선택합니다.
단순한 작업에 그림을 추가하거나 아래 여덟 관점을 모두 작성하지 않습니다. 정적 구조는 Mermaid로, 검증 범위는 표로 표현할 수 있습니다.

## 관점 선택

| 관점 | 확인할 질문 | 필요한 입력 | 표현 |
| --- | --- | --- | --- |
| 시나리오 | 특정 조건에서 어떤 일이 순서대로 일어나는가? | 시작 조건, 행동과 관찰 결과 | 한 경로의 흐름도 |
| 상태 전이 | 어떤 상태로 이동할 수 있고 조건은 무엇인가? | 상태, 이벤트, 조건과 다음 상태 | 상태표와 상태도 |
| 코드 실행 | 어떤 처리와 분기를 거치는가? | 유닛의 로직 또는 읽은 함수 | 분기 흐름도 |
| 상호작용 | 누가 누구에게 요청하고 응답하는가? | 구성 요소, 메시지와 순서 | 순서도 (`sequenceDiagram`) |
| 데이터 | 값이 어디서 생기고 어떻게 바뀌는가? | 입력, 변환, 저장·응답과 출력 | 값과 변환의 흐름도 |
| 구조·의존 | 무엇이 무엇을 사용하는가? | 모듈, 함수, 타입과 의존 방향 | 의존 관계도 |
| 변경 영향 | 바꾸면 어디를 확인해야 하는가? | 변경 대상과 확인한 사용처 | 영향 관계도 |
| 검증 범위 | 무엇을 실행했고 무엇이 남았는가? | TC, 환경, 결과와 실행 기록 | TC·결과·근거 표 |

시나리오는 구체적인 한 경로이고 상태도는 허용된 이동을 모읍니다. 의존 화살표는 실행 순서를 뜻하지 않습니다.
영향을 아직 확인하지 않았으면 영향 후보로 표시합니다. 변경 전후 비교는 각 관점에 적용하며 별도 관점으로 늘리지 않습니다.
[검색 기능의 여덟 예시](visualization-examples.md)에서 관점의 차이를 확인합니다.

## 근거 표시

그림 가까이에 대상, 관점, 근거와 범위를 문장 또는 표로 적습니다. 새 frontmatter는 요구하지 않습니다.

| 근거 | 기록할 것 | 주장할 수 있는 범위 |
| --- | --- | --- |
| 명세 기준 | wiki 경로·섹션과 합의한 조건 | 기대 동작 |
| 코드 해석 | 읽은 경로·함수와 커밋 또는 현재 diff | 코드에서 파악한 처리·의존. 실행 결과는 미검증 |
| 실행 관측 | 환경, 입력·TC, 실행 시점과 로그·결과 위치 | 실제로 실행하고 관측한 범위 |

가상 예시는 가상이라고 표시합니다. 예시의 테스트 결과를 실행 근거로 쓰지 않습니다.
근거가 섞이면 기대와 구현·관측을 나누고 각 출처를 적습니다. 읽지 않은 코드나 실행하지 않은 경로를 관측으로 표시하지 않습니다.
명세와 구현이 다르면 불일치를 보고합니다. 그림에 맞추려고 합의된 명세를 바꾸지 않습니다.
그림의 의미에 색을 쓰면 글자나 모양으로도 구분합니다. 비밀값과 실제 사용자 데이터는 넣지 않습니다.

## wiki 작성

기능의 시나리오·상태·상호작용·데이터는 기존 `## 흐름`에 둡니다. 단위 함수의 분기는 `## 내부 로직`에 둡니다.
구조와 영향은 해당 명세의 관계 표에 대응시킵니다. 검증의 실제 실행 결과는 PR이나 검증 기록에 남깁니다.
그림은 표와 문장을 보완합니다. 표시할 수 없는 환경에서도 같은 조건·결과·관계를 읽을 수 있어야 합니다.
정확한 함수 계약·타입 선언은 유닛·타입 페이지로 연결합니다. 그림 안에 별도 계약을 만들지 않습니다.
상태별 표시나 허용 조작이 달라지는 UI 기능을 새로 작성·변경하면 [UI 패턴](ui-async-pattern.md)의 상태표와 상태도를 적용합니다.
정적 화면처럼 전이가 없으면 상태도를 생략합니다. 상태도 적용을 검토한 작업에서는 생략 이유를 짧게 적습니다.

## spec에서 확인

1. 사용자가 정하려는 동작과 기존 명세를 확인하고 필요한 관점을 고릅니다.
2. UI이면 초기 진입, 이벤트·조건, 성공·빈 결과·오류와 재시도·취소 중 해당하는 경로를 확인합니다.
3. 동시 요청·늦은 응답처럼 제품의 결정이 빠졌으면 질문합니다. 예시의 동작을 그대로 채택하지 않습니다.
4. 합의한 관찰 결과와 경계를 이슈의 `What`·`Acceptance`에 적고 대상 wiki를 연결합니다.
5. 그림이 합의에 필요하면 초안과 근거를 표시합니다. spec 단계에서 대상 wiki·구현을 변경하지 않습니다.

## audit에서 확인

1. 지정한 범위의 그림과 그 근거를 읽습니다. 여덟 관점 전체를 새로 만들도록 요구하지 않습니다.
2. 표·문장과 그림의 상태·전이·조건·순서·관계를 양방향으로 대조합니다. 한쪽에만 있는 항목을 찾습니다.
3. 담당 유닛·타입·TC의 연결과 실제 내용을 확인합니다. UI는 상태 유지와 늦은 응답·취소 경로도 대조합니다.
4. 명세 기준의 기대와 코드 해석·실행 관측을 비교합니다. 근거 없는 영향 추정과 가상 결과를 구분합니다.
5. 완료 기준별 실행 기록을 확인합니다. 그림 표시·문서 일치와 동작 검증을 구분하고 미실행은 `미검증`으로 보고합니다.
6. 기존 audit 분류·심각도로 위치, 규칙, 영향과 필요한 조치를 보고합니다. 대상 파일은 수정하지 않습니다.

서버나 시뮬레이터는 필요하지 않습니다. 자동 생성·의미 판정·실제 화면 실행을 했다고 이 기준만으로 주장하지 않습니다.
