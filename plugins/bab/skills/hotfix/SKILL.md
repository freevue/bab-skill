# bab hotfix

사용자가 핫픽스나 긴급한 버그 수정을 요청할 때 사용합니다. 장애 설명 또는 기존 이슈 번호를 받습니다.
검증 범위를 정하는 진입 스킬입니다. 이슈·wiki·구현·PR 절차를 새로 만들지 않습니다.

마일스톤을 도입한 프로젝트는 [공통 sync 범위](../milestone/references/protocol.md#sync에서-소비)를 따릅니다.
긴급 작업이 현재 목표 밖에 있으면 사용자의 범위 변경 지시를 먼저 반영합니다.

## 진입

1. 실제 저장소와 원격, 대상 경로의 지침을 확인합니다. 증상·재현 조건·기대 동작을 현재 대화와 이슈에서 읽습니다.
2. 빠진 결정만 질문합니다. 추측으로 기대 동작을 정하거나 이미 확인한 승인·결정을 다시 묻지 않습니다.
3. 기존 이슈가 있으면 재사용합니다. 등록·확정이 필요하면 [spec](../spec/SKILL.md)의 필수 항목과 승인 기준을 따릅니다.
4. [검증 계획과 실행 근거](../sync/references/verification.md)를 읽고 핫픽스 검증 계획을 작성합니다.
5. [sync](../sync/SKILL.md)에 아래 인계 내용을 전달합니다. sync의 선점과 이슈 게이트를 통과한 뒤 기존 순서로 작업합니다.

| 인계 항목 | 내용 |
| --- | --- |
| 대상 | 확인한 저장소·이슈와 사용자가 승인한 작업·원격 변경 범위 |
| 모드 | 사용자의 핫픽스 요청 근거와 핫픽스 검증 계획 |
| 동작 | 재현 조건·기대 결과·완료 기준과 관련 TC |
| 검증 | 변경·영향 경계, 선택·제외한 검사와 이유, 실제 명령과 로컬·CI 실행 주체 |
| 확대·기록 | 전체 확대 사유, 이미 실행한 검증 기록과 대기 중인 CI |

새 결정이나 이슈 확정이 필요하면 기존 spec 기준으로 처리합니다. 핫픽스나 P0·P1이라는 이름이 승인을 대신하지 않습니다.
확정·선점·브랜치·wiki·실패 테스트·구현·검증·PR·현재 커밋 CI는 기존 sync 절차를 따릅니다.
범위를 벗어나는 실패와 중단, 머지·배포도 기존 지시를 따릅니다.

## 검증과 보고

sync는 공통 기준으로 검증하고 [audit](../audit/SKILL.md)에 계획과 실행 기록을 넘깁니다.
audit은 유효한 결과를 재사용하고 명세·코드·완료 기준을 대조합니다. 입력·조건이 바뀌거나 근거가 없으면 해당 검사를 다시 수행합니다.
전체 검증을 기존 CI가 담당하면 현재 PR 커밋의 결과를 사용합니다. 별도 로컬 실행 규칙이 없으면 같은 전체 검사를 추가 요구하지 않습니다.
일반 sync의 기본 범위를 이 스킬로 일괄 바꾸지 않습니다. 이슈 없는 작은 문서 수정의 `no-spec`을 핫픽스 예외로 쓰지 않습니다.

[공통 브리핑 규칙](../setup/assets/claude-section.md#최종-브리핑)으로 결과를 전합니다.
선택한 범위와 확대 이유, 직접 실행·재사용·대기·미검증을 구분합니다. 근거 없는 동작 통과나 시간 절약을 주장하지 않습니다.

예시:

```text
bab:hotfix로 이슈 #12의 페이지 번호 버그를 수정해줘.
재현 조건과 기존 계약을 확인하고 영향 범위에 맞춰 검증해줘.
검증 후 승인한 범위에서 커밋·푸시하고 PR을 열어줘.
```
